0O que é o Node-RED

Node-RED é um runtime de automação baseado em fluxos: a lógica é montada ligando nós (caixas) por fios, e cada mensagem (msg, um objeto JS com msg.payload) percorre esses fios de nó em nó. Nas centrais MyIO (Orange Pi com Linux) ele roda embarcado pelo myio-api.service e faz a ponte entre os medidores no campo (Modbus/MQTT) e a nuvem — expondo a REST local em /api/* (porta 8080), onde GCDR, Alarmes, ThingsBoard e o App disparam chamadas como POST /api/setMqttSyncStatus. Os nós function são blocos de JavaScript; o estado entre execuções fica no contexto global (em memória por padrão). Editor em /red.

3Concorrência multi-sistema (o problema resolvido)

GCDR e Alarmes pausam ao mesmo tempo. Com boolean (last-writer-wins) o MQTT voltaria cedo demais; com holds, não.

sequenceDiagram autonumber participant G as GCDR participant A as Alarmes participant N as Node-RED participant M as MQTT Note over M: enable (0 holds) G->>N: DISABLE hold=gcdr:provisioning (ttl 900s) N->>M: disable (holds=1) A->>N: DISABLE hold=alarms:storm (ttl 300s) N-->>N: holds=2 G->>N: ENABLE hold=gcdr:provisioning N-->>N: holds=1 Note over N,M: boolean voltaria aqui (errado)
holds: continua disable A->>N: ENABLE hold=alarms:storm N->>M: enable (holds=0)

4Dead-man switch (TTL) — auto-recuperação

Um sistema desabilita e cai sem reabilitar. O hold expira pelo TTL e o MQTT volta sozinho.

sequenceDiagram autonumber participant A as Alarmes participant N as Node-RED participant M as MQTT A->>N: DISABLE hold=alarms:storm (ttl 300s) N->>M: disable (holds=1) Note over A: instância cai (nunca manda ENABLE) Note over N: ...300s depois... N->>N: TTL sweep (próximo GET/POST/timer) N->>M: enable (holds=0) — volta sozinho

Por que mais robusto: os holds + reference counting acabam com o last-writer-wins entre GCDR/Alarmes/TB/App; o TTL / dead-man switch garante que o MQTT nunca fique preso desabilitado se um sistema cair; e separar request × record × response elimina redundância — o resultado é sempre do servidor.
